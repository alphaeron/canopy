# Review server

`canopyweb` is the review server, a separate binary from the CLI (`go build ./cmd/canopyweb`). At startup it loads the configuration, selects the platform, and refuses to start unless that platform's section is complete and valid (GitHub: `app_id`, `private_key`, and `webhook_secret` all set, `app_id` numeric, `private_key` an RSA key), and unless `review_workers` × `review_queue_per_worker` is at most 4096. `--addr` overrides `serve_addr`, and `--config` names the configuration file.

| Route | Purpose |
|---|---|
| `POST /webhooks/github` | The GitHub App's webhook; each platform chooses its own webhook path. The signature is verified before anything else; unsigned or mis-signed requests get 401. A reviewable event is acknowledged with 202 and reviewed in the background; a full queue gets 503. Only the newest review of a pull request's head commit reports (see below). |
| `GET /openapi.json`, `GET /openapi.yaml` | The OpenAPI 3.1 document, generated from the routes |
| `GET /swagger` | Interactive API documentation |
| `GET /reviews/{owner}/{name}/{number}/{sha}?exp=…&sig=…` | The review page of a pull request's head commit (with `public_url` and `link_key`; see [Review pages](#review-pages)) |
| `GET /reviews/{owner}/{name}/{number}/{sha}/progress?exp=…&sig=…` | How far that commit's newest review has come, as JSON, which the review page polls |

On GitHub, the server runs as a GitHub App. It needs these repository permissions: *Contents* (read), *Pull requests* (read, which also covers reading a pull request's labels), *Checks* (read and write), and *Members* (organization, read) to expand `org/team` targets. It reviews on `pull_request` (`opened`, `synchronize`, `reopened`, `ready_for_review`, `labeled`, `unlabeled`, and `edited` when the base branch changes) and `pull_request_review` (`submitted`, `dismissed`) events, except those of a closed or merged pull request (a reopened one is reviewed again). Subscribe it to `push` events too: a push to a repository's default branch starts no review, but the server reads the pushed commit's tree and the rules files the push added or changed into its cache in the background, so the reviews of pull requests based on that commit start with them cached. Requests that GitHub rate-limits are retried after the delay it asks for: up to a minute for a secondary limit (`Retry-After`), and for an exhausted primary limit until it resets, within the review's deadline (at most 10 minutes). A review still rate-limited reports `rate limited by the platform; try again later`; other errors are not retried.

Each review runs with a timeout (`review_timeout`); a review that times out reports `review timed out`, allowing up to `report_timeout` to post it. Stopping the server (SIGINT or SIGTERM) cancels reviews in flight and waits up to `shutdown_timeout` for open requests.

Webhooks can arrive in bursts (several reviews submitted at once, pushes in a row), and GitHub does not order them. The server reviews one pull request's head commit at a time, and only its newest review reports: a webhook for a head commit already waiting for a worker replaces the waiting review, one for a head commit under review cancels that review and is reviewed next, and a review that a newer one supersedes after it ran does not report. Each review reads the approvals when it runs, so the last review to report has seen the latest. Without a database this holds within one server process, and replicas behind a load balancer do not coordinate. With a database (`database_url`), replicas order their reports through it: a review reports only if no review of its pull request requested later has reported (for any head commit), one at a time per pull request. A review whose order cannot be recorded (the database is unavailable) reports anything but a pass as is, and a pass as `review could not be recorded; see the server logs`, so a review that may be stale never passes a pull request.

## Review pages

With `public_url` and `link_key` set, every review has a page, and the check runs the server creates link to it (as the check's details URL, and at the end of its summary). The page follows the newest review of the pull request's head commit: before any review it says none has been recorded yet; while the review is queued or running it shows its stage (waiting for a worker, reading the pull request, fetching rules files, matching rules to files, resolving approver targets, evaluating approvals file by file, publishing the check) and updates itself; once the review finishes it shows the verdict and the full decision path of every file (rules file → rule → approver target), the errors, and the event trace (the first 2,000 events). The page is self-contained (inline styles and scripts, nothing loaded from elsewhere) and readable without JavaScript, which only adds search, filters, and the live updates.

Live progress comes from the server running the review; another replica's page shows the review as running, from the database, until it finishes. Without a database a server shows only the reviews it queued or ran recently (its 32 most recently finished).

A page shows a repository's paths, approvers, and review errors, so it is served only for a link the server signed with `link_key`: anyone who can see the check run can open its page, and a link for any other pull request or commit is not found. A link expires `link_lifetime` (90 days by default) after the server signs it, and each review signs a fresh one; until then, treat it like the check run it came from.

Each review also marks its check run in progress as it starts evaluating, and its report waits for that, so a pull request shows the review running rather than the previous result. A review still waiting for a worker half a second after its webhook arrived marks its check run queued first (one a free worker starts at once costs no request for it). With a database both are ordered like reports: a review never marks its pull request queued or running after a newer review reported, and a review whose order is unknown does not mark it at all. A review cancelled because the server is stopping leaves its check in progress until the next review of the pull request.

## Database

With `database_url` set, the server keeps what it reads from GitHub that cannot go stale (base tree listings by commit, rules files by blob SHA) in PostgreSQL, shared by every replica, behind its in-memory cache, and records every verified webhook delivery and every review: its pull request and revisions, approvals, owners, and labels, the full review state, the outcome it published, the approver targets it evaluated, and its timings. The record is never read back to decide a review. A team's members, a user, and a pull request's reviews and labels can change, so they are read from GitHub on every review; the last answer is kept with its ETag and used only when GitHub confirms it is unchanged (a `304 Not Modified`, which does not count against the rate limit). Cached rows are authenticated with `database_key`, which never reaches the database, and a rules file is checked against its SHA, so write access to the database alone cannot change the rules or team members a review sees. The server prunes the cache hourly (tree listings and team, user, review, and label responses after a week, rules files after a month; a pruned entry costs one more read from GitHub) and the ordering of a pull request after a month without reviews; the record of deliveries and reviews is kept. The server creates its tables at startup; while the project is in development, a schema change means recreating the database.

A pull request's changed files come from GitHub's comparison of the base and head commits the webhook names, never from the pull request's file listing, which GitHub answers for whatever the head is by then. A comparison listing as many files as GitHub lists (300), or none, is confirmed from the merge-base and head trees, with a warning that it is large when it was cut short; a base tree too large for one listing is listed a directory at a time. One that still cannot be listed completely errors rather than being reviewed incompletely.
